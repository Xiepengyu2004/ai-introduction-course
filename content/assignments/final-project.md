# Final Project：研究探索与 AI 创意实践

Final Project 是本课程的综合实践项目，占课程总评 **30 分**。项目于 **2026 年 11 月 3 日发布**，最终路演安排在 **2026 年 12 月 22 日至 12 月 28 日**。

本项目为**个人项目**。每位同学需要独立完成选题、实现、实验或测试、论文撰写与最终路演，不接受组队提交。

你可以选择以下任一赛道：

- **Research Track（研究型）**：围绕一个明确的问题完成 baseline、对比实验、分析与结论。
- **Build Track（创意型）**：围绕真实使用场景构建一个可运行的 AI 应用或交互原型。

下面列出的题目是推荐方向，**不是限定题目**。两个赛道均允许自选课题，但自选题需要在 Proposal 阶段说明与人工智能的关联、预期成果、技术可行性和七周内的完成范围。

> 无论选择哪个 Track，最终都需要提交论文、源代码和项目结果，并参加路演。

## 赛道一：Research Track（研究型）

Research Track 适合希望体验小型科研流程的同学。项目不要求提出全新的理论，但必须有一个**可以通过实验回答的研究问题**。

完整项目通常应包含：

```text
研究问题 → 相关工作 → Baseline → 改进或变量控制
        → 对比/消融实验 → 结果分析 → 结论与局限
```

### 推荐题目 R1：Can Better Prompts Replace Fine-tuning?

围绕视觉语言模型中的 prompt 设计，研究更好的提示词能否在部分场景中替代模型微调。

> **必读论文：** Kaiyang Zhou, Jingkang Yang, Chen Change Loy, Ziwei Liu. [Learning to Prompt for Vision-Language Models](https://arxiv.org/abs/2109.01134). IJCV, 2022. 重点阅读 CoOp 如何将 prompt 的上下文词改为可学习向量，以及它与手工 prompt、Zero-shot CLIP 在少样本场景中的比较方式。思考：论文中的 prompt learning 本身也是一种参数学习，因此你需要在项目中明确定义“替代 fine-tuning”具体指替代哪一类微调。

可以选择的实验方向包括：

- 使用 CLIP 比较 Zero-shot、Prompt Templates、Linear Probe 和少样本适配。
- 比较不同 prompt 长度、描述粒度和模板数量。
- 研究样本数量变化对 prompt 方法与微调方法的影响。
- 比较性能、训练成本、推理成本和适用场景。

项目应明确数据集、评价指标与公平对比设置，不能只展示少量成功案例。

### 推荐题目 R2：How Low Can the Rank Go?

研究 LoRA 中 rank 对模型效果、可训练参数量、显存占用和训练速度的影响。

> **必读论文：** Edward J. Hu et al. [LoRA: Low-Rank Adaptation of Large Language Models](https://arxiv.org/abs/2106.09685). ICLR, 2022. 重点理解 LoRA 如何冻结预训练权重，并用两个低秩矩阵表示权重更新；同时阅读论文关于 rank、可训练参数量、训练效率和 rank-deficiency 的实验与讨论。这篇论文是设计 rank 对照实验和解释结果的基础。

建议使用较小的语言模型或 Transformer，在相同数据和训练预算下比较：

```text
rank = 2、4、8、16
```

至少应报告：

- 任务性能指标。
- 可训练参数量。
- 训练时间或显存占用。
- rank 继续降低时性能下降的趋势与原因分析。

重点不是单纯找到最高分，而是解释性能与效率之间的权衡。

### 推荐题目 R3：How Much Masking Is Too Much?

复现一个小型 Masked Autoencoder，研究掩码率对重建效果和下游任务表现的影响。

> **必读论文：** Kaiming He, Xinlei Chen, Saining Xie, Yanghao Li, Piotr Dollár, Ross Girshick. [Masked Autoencoders Are Scalable Vision Learners](https://arxiv.org/abs/2111.06377). CVPR, 2022. 重点阅读非对称 encoder-decoder 结构、只编码可见 patch 的设计，以及 masking ratio 的消融实验。特别关注论文为什么采用较高的 75% 掩码率，以及重建目标和下游表征质量之间的关系。

建议至少比较：

```text
mask ratio = 50%、75%、90%
```

可以从以下角度分析：

- 重建误差与可视化结果。
- 下游分类或线性探测性能。
- 收敛速度和训练稳定性。
- 为什么更好的重建结果不一定意味着更好的表征。

### Research Track 自选题要求

自选研究题目需要在 Proposal 中写清楚：

1. 一个具体、可回答的研究问题。
2. 至少一个可以复现的 baseline。
3. 使用的数据集和评价指标。
4. 需要控制或比较的变量。
5. 预期实验表格或图表。
6. 计算资源需求和备用方案。

范围应足够小，确保能在七周内完成完整实验和分析。仅训练一个模型并报告最终准确率，不构成完整的研究型项目。

## 赛道二：Build Track（创意型）

Build Track 适合希望把 AI 技术做成实际应用的同学。项目应包含可运行的核心流程，不要求开发大而全的产品，但需要有一个稳定、清楚、可以现场展示的 MVP。

完整项目通常应包含：

```text
用户与场景 → 核心问题 → AI 模块 → MVP
          → 功能测试与效果评估 → Demo 与总结
```

### 推荐题目 B1：以图搜图（Visual Search Engine）

用户上传一张图片，系统从图库中返回视觉或语义上最相似的图片。

建议的最小实现：

- 使用 CLIP 或其他视觉编码器提取图片特征。
- 建立一个小型图片库及向量索引。
- 支持上传图片并返回 Top-K 相似结果。
- 展示相似度或排序结果。
- 使用若干查询样例分析成功案例和失败案例。

可以继续扩展自然语言检索，例如输入“秋天、戴帽子的猫、红色汽车”等描述搜索图片。

### 推荐题目 B2：会聊天的虚拟角色（Interactive AI Character）

设计一个具有稳定身份、记忆和交互方式的虚拟角色，使其能够围绕设定与用户连续对话。

建议的最小实现：

- 明确角色背景、性格、说话方式和行为边界。
- 支持多轮对话。
- 实现短期记忆或可控的长期记忆。
- 提供文本界面，也可以增加语音、表情或虚拟形象。
- 设计一致性、记忆正确性和安全性的测试样例。

项目重点不只是调用聊天 API，还需要说明角色设定、记忆机制、上下文组织和效果评估。

### 推荐题目 B3：AI 房间改造助手（Room Designer）

用户上传房间照片并描述需求，系统提供布局、风格或局部改造建议，也可以生成辅助效果图。

建议的最小实现：

- 上传房间图片并识别主要区域或物体。
- 接收自然语言需求，如“改成适合学习的简约卧室”。
- 输出结构化改造建议、物品清单或布局说明。
- 可选：加入目标区域标注、局部图像编辑或效果图生成。
- 对建议的合理性、一致性和可执行性进行案例分析。

建议聚焦一项核心能力，不要求从零训练完整的图像生成系统。

### 推荐题目 B4：本科生全周期学习陪伴 Agent

构建一个面向本科阶段学习的课程陪伴 Agent，帮助学生理解知识、整理材料和进行复习测验。

建议先聚焦一门课程或一个学期，最小实现可以包含：

- 导入课程 PPT、讲义或个人笔记。
- 按章节整理知识点和术语。
- 基于课程材料回答问题，并标明答案依据。
- 按指定章节和难度生成练习题或模拟考试题。
- 记录错题或薄弱知识点，生成后续复习建议。

可以进一步扩展课程时间线、学习计划、多课程知识库和长期学习画像。

需要特别注意：

- 回答应尽量能够追溯到课程材料，减少无依据生成。
- 不应自动代替学生完成需要独立提交的课程作业。
- 不得上传未经授权的私人材料、个人信息或受限制的课程资源。
- 应通过问答正确性、引用可靠性、出题质量或用户测试评价实际效果。

### Build Track 自选题要求

自选创意项目需要在 Proposal 中写清楚：

1. 目标用户和具体使用场景。
2. 要解决的核心问题。
3. 核心 AI 模块及其必要性。
4. 七周内必须完成的 MVP。
5. 效果评估方式和测试样例。
6. 数据、模型、API 和计算资源需求。
7. 网络或 API 不可用时的备用演示方案。

仅制作静态页面，或只对现成 API 进行简单包装而没有系统设计、测试和分析，不能视为完整的创意型项目。

## Final Report 要求

两个 Track 都需要提交 4–6 页论文。建议使用以下结构。

### Research Track

1. Abstract。
2. 研究背景与问题定义。
3. Related Work。
4. 方法与实验设计。
5. 实验结果与分析。
6. 消融实验或进一步讨论。
7. 结论、局限与未来工作。
8. 参考文献。

### Build Track

1. Abstract。
2. 使用场景与需求分析。
3. 系统设计与核心 AI 方法。
4. 实现细节。
5. 测试方案与结果。
6. Demo 效果、失败案例与局限。
7. 结论与未来改进。
8. 参考文献。

报告不能只记录开发步骤。Research Track 需要解释实验结果，Build Track 也需要提供可验证的测试、案例或用户反馈。

## 提醒

- 不要使用测试集反复调参；Research Track 应保留独立测试或最终评估数据。
- 记录随机种子、数据划分、模型版本和关键超参数。
- 使用外部模型、数据、代码、API 或 AI 辅助工具时，必须在报告中说明并正确引用。
- 不得提交含有个人隐私、未经授权数据或密钥的代码和材料。
- Proposal、Milestone、Final Report、代码与路演均须由本人独立完成，不接受团队作品或多人共同提交同一项目。
- 项目源代码不得包含 API Key、访问令牌或账号密码。
- 不得将课程要求禁止公开的材料上传到公开仓库。
